# ビジネス部門 本人加筆ガイド（B1 自治体向け公共交通 再編シナリオ比較）

目的: 生成AIの出力そのままと見なされないよう（募集要項の生成AI条項）、本人の経験・判断を入れる。
【本人加筆: …】の括弧書き全体（【】含む）を、本人の文に置き換える。括弧書きの長さ程度に収めると上限内に収まる。置換後に必ず `python3 contests/ichibiz-2026/check_limits_divisions.py` を実行する。
置き換えたら submission 直下の4ファイル（title/problem/service/background）にも同じ内容をコピーする（検査スクリプトが一致を確認する）。

| 場所 | 問いかけ | 書き方のヒント |
|---|---|---|
| problem.md 1段落目末 | 公共交通の見直しで困った・困っている人の話を聞いたことはあるか。担当者や住民の声は | 「いつ・どこで・誰が・何に困ったか」を1〜2文。伝聞なら誰から聞いたかも |
| service.md 末尾 | 担当者が実際にどんな場面（協議会、住民説明会、庁内会議）でこの画面を使うと想像するか | 具体的な場面を1文。想像でよいが、想像だと分かる書き方に |
| market.md ニーズ段落 | 自治体職員・事業者・コンサルに話を聞けたか。聞けていないなら誰に何を聞くか | 聞けた場合は1文で内容。未聞なら「〇〇市の担当者に△△を聞く予定」。嘘のヒアリングは書かない |
| challenges.md 末尾 | いまの体制は。相談できる自治体・事業者・専門家は。次の一手は | 個人か仲間がいるか、期限付きの次の一手（例: 住民向けアプリの公開、1自治体への相談） |
| background.md 冒頭 | 自分が公共交通で困った場面、または身近な人の移動の困りごと | 具体的な1場面。最も重要な加筆 |
| background.md 2か所目 | 住民向けアプリを作っていて「計画側に必要」と気づいたのは、実際にはどういう出来事か | 実際の経緯に合わせて、AI草稿の文を自分の言葉に書き換える。違うなら削除して書き直す |
| background.md 3か所目 | GTFS整備などで実際にぶつかった壁は何か | 例: 欠損、事業者間の停留所名のずれ（実際に起きた事実のみ） |
| background.md 末尾 | アプリの開発状況（対象地域・できていること） | 事実のみ。誇張しない |

提出前の確認
- 「開発中」「実証になっている」の記述が、提出時点の実際の状況と合っているか（住民向けアプリの進捗）。合わなければ service.md の該当文を直す。
- 住民向けアプリ（ODPT応募）と本事業の役割分担（住民向け＝無償の診断、本事業＝担当者向けの変更案比較）が、ODPT側の説明と矛盾しないか。
- 本人の言葉にしたあと、全体の文体が不自然に混ざっていないか読み直す。
