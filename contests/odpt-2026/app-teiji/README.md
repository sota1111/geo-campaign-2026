# バス定時性カルテ（新案 N2・第1版）

バスの位置データ（GTFS-RT）を蓄積し、時刻表（GTFS）と突き合わせて、路線×時間帯の定時率・区間ごとに増える遅れ・団子運転を、事業者・自治体向けに見える化する。現行の生活アクセス診断マップ（`../app/`）とは別に追加した案で、現行アプリ・`submission/description.md`・`web/data` には触れていない。流用元（`lifemap/gtfs.py` の時刻・運行判定、`tests/helpers.py` の合成 GTFS 作成、地図 UI の構成）はコピーして改変した。

状態: **動く第1版**。取得・品質測定・遅れ推定・集計・画面・CSV・テスト（55 件）まで通る。ただし**実データの昼間の品質はまだ測れていない**（この作業は日本時間 11/13 0:00〜0:25 で、車両がほとんど走っていない時間帯だった）。ゲート判定は昼間の再測定が必要。数週間の常駐取得は総司令官の判断事項のため、起動していない。cron や GitHub Actions の設定も作っていない。

## 構成

| パス | 役割 |
|---|---|
| `teiji/gtfsrt.py` | GTFS-RT（Protocol Buffers）を標準ライブラリだけで読む。VehiclePosition / TripUpdate。合成データ作成用の書き出しも持つ |
| `teiji/ckan.py`, `teiji/discover.py` | ckan.odpt.org の公開ページ（HTML）から、CC BY 4.0 のバス GTFS-RT と静的 GTFS の URL を探す。結果は `data/sources.json`（24 データセット、全てトークン不要の `api-public.odpt.org`） |
| `teiji/collect.py` | 一定間隔で取得して `data/raw/<dataset>/<日付>.jsonl` に保存。GET のみ。`--duration` で必ず止まる |
| `teiji/fetch_gtfs.py` | 静的 GTFS を `data/gtfs/` に保存 |
| `teiji/quality.py` | データ品質の測定とゲート判定（事業者別）。`--markdown` で表を出す |
| `teiji/delay.py` | 位置と時刻表から停留所ごとの通過時刻・遅れを推定 |
| `teiji/aggregate.py` | 路線×時間帯の定時率、区間の遅れ、団子運転・間延びの集計 |
| `teiji/build.py` | 公開集計（`web/data/`）と事業者向け詳細 CSV（`out/operator-detail/`）を作る |
| `teiji/demo.py` | 画面確認用の合成データ（実在しない事業者）。`web/data-demo/` に出力 |
| `web/` | 静的サイト（地図・表・CSV 保存）。MapLibre GL JS と地理院タイル |
| `tests/` | unittest 55 件（うち 1 件は画面の純粋関数 `tests/lib_test.js` を node で実行） |
| `data/quality.json` | 直近の品質測定結果 |

## 手順（すべて手動。`app-teiji/` で実行）

```
python3 -m teiji.fetch_gtfs                        # 静的GTFS（初回のみ、約19MB）
python3 -m teiji.collect --interval 30 --duration 3600   # 昼間に1時間。事業者24件、GETのみ
python3 -m teiji.quality --markdown                # 事業者別の品質と判定（表を出力）
python3 -m teiji.build                             # web/data/ と out/operator-detail/ を作る
cd web && python3 -m http.server 8000              # http://127.0.0.1:8000/ を開く（file:// では動かない）
python3 -m unittest discover -s tests              # テスト
python3 -m teiji.demo                              # 合成デモ。http://127.0.0.1:8000/?data=data-demo
```

- `collect` の間隔は 15 秒未満にできない。全事業者を 1 回取るごとに最大 47 リクエスト（車両位置 24 + TripUpdate 23）。負荷を抑えたいときは `--only odpt_gunma_bus_all_lines,b_bus_gtfs_rt-toei` で絞り、`--no-trip-updates` で TripUpdate を外す。
- **昼間の再実行（ゲートの確認）**: 平日の 9〜10 時か 12〜13 時に、上の `collect` を 1 時間回し、`quality --markdown` を見る。日中（7〜19 時）の取得が 10 回未満だと「判定不能」になる。昼間の車両数が多い事業者が分かったら `--only` で絞って 1 日回すと、遅れ推定まで確認できる。
- 数週間の連続取得は、誰がどこで動かすかを総司令官が決めてから。参考として、`--duration 86400` を日ごとに繰り返す形が最小構成になる。データ量は 1 車両 1 回あたり約 100 バイト（JSONL）で、都営バスのように数百台が走る事業者を 60 秒間隔で取ると 1 日あたり数十 MB の規模と見込まれる（概算で未測定）。
- 画面は `?data=<フォルダ名>` で別の集計フォルダを読める（英小文字・数字・ハイフンのみ）。

## ゲート判定の閾値と、通過の見込み

偵察隊のゲート（11/14〜16 の昼間に 3 事業者で車両数・更新間隔・trip_id 一致を確認）の閾値は、工兵が次の通り設定した（`quality.py` の `GATE`）。根拠のある基準値ではなく、第1版の初期値。

| 項目 | 閾値 | 理由（仮定） |
|---|---|---|
| 取得成功率 | 95% 以上 | 欠測が多いと遅れの推定間隔が空く |
| 日中（7〜19 時）の車両数の中央値 | 5 台以上 | 路線×時間帯の集計に 10 便以上が要る（`aggregate.py` の MIN_TRIPS）。1 日の稼働便数で決まるため、1 台では数週間かかる |
| 位置更新間隔（車両ごと・中央値） | 90 秒以下 | 停留所間が 1〜2 分のバスで、補間の上限 300 秒に余裕を持たせる |
| 運行日の trip_id 一致率 | 90% 以上 | 一致しない便は遅れを出せない |
| 日中の取得回数 | 10 回以上 | これ未満は「判定不能」 |

**通りそうか: 現時点では言えない（判定不能）。** 見込みは次の通り。

- 良い材料: 40/40 の疎通、約 30 秒周期の更新、TripUpdate に 0 以外の遅れ値が入ること、車両がいた事業者の trip_id が（少数だが）一致したこと。
- 悪い材料・不明: 都営バスが 0 台だったこと。コミュニティバス中心の事業者（きよバス、須崎市、土佐市など）は稼働車両が少なく、「5 台以上」を満たさない公算が大きい。須崎市で trip_id 不一致があったこと。
- 見込み: 都営バス・仙台市交通局・とさでん交通・群馬の事業者・日本中央バスのような車両数の多い事業者が、昼間に 3 事業者通るかが分かれ目。通ったとしても、小規模事業者は「サンプル不足」が長く続く。**昼間 1 時間の再測定で判断できる。**

## 遅れ推定の方法と限界

- 停留所を結ぶ折れ線に車両位置を射影し、連続する 2 観測の間の停留所通過時刻を線形補間して、時刻表との差を遅れとする。道路形状（shapes）は使わない。
- 次の場合は推定しない: 折れ線から 200m 超離れた観測、2 観測の間隔が 300 秒超または 3000m 超、運行時間帯（始発の 30 分前〜終点の 90 分後）の外の観測、遅れが 2 時間を超える推定。
- 合成データで検証したこと: 一定の遅れ・早発・区間ごとの遅れの増加を数秒の誤差で復元する、観測の抜けや路線外の点を使わない、24 時超の便を運行日を取り違えずに扱う（テスト `test_delay.py`）。
- **実データとの突き合わせは未実施**。計画上は 12/5 に便 10 本程度を時刻表と目視で突き合わせる。精度（数十秒以内か）は実データで測るまで言えない。
- 定時（1 分早い〜5 分遅い）、団子運転（時刻表間隔の 25% 未満、時刻表間隔 1〜20 分の停留所）、サンプル不足（便数 10 未満または観測 50 未満、団子運転は組 20 未満）の基準は、見せ方の仮定で、画面と説明に明記している。事業者へのヒアリングで見直す前提。
- 祝日・臨時ダイヤ・運休は反映しない。1 本の便が複数回 trip_id を変える配信や、位置の無い車両は集計に入らない。

## 公開と事業者向けの分離

- `web/data/`（公開）: 路線×時間帯、区間、停留所の集計だけ。サンプル不足の行は数値を出さない。trip_id・車両 ID は含めない（テストあり）。事業者を並べるときは名称順で、順位・得点の項目や並べ替えは作らない（テストで項目の有無を確認）。
- `out/operator-detail/<事業者>/`（事業者向け・`.gitignore` 対象）: `routes.csv`、`segments.csv`、`stops.csv`、`trips.csv`（便ごとの推定通過時刻と遅れ）。公開ホスティングには置かない。
- 画面のボタンで保存できる CSV は、公開集計と同じ内容（路線×時間帯、区間）。

## ライセンスと取得の作法

- CC BY 4.0 のデータだけを使う。`discover` は CKAN のライセンス表記が CC BY 4.0 で、`api-public.odpt.org`（トークン不要）の URL のものだけを採用する。チャレンジ限定・基本ライセンス、consumerKey 付きの URL は採用しない（テストあり）。
- 画面に、事業者名・公共交通オープンデータセンター・CC BY 4.0、位置からの推定・集計という加工の旨、地理院タイルの出典を表示する。
- 取得は GET のみ。User-Agent に用途を入れている。`.env`・`secrets/` は読んでいない。

## 判断ログ（指示外・解釈に幅があった箇所）

- **偵察隊の試作物が使えなかった**: 指示にある `sandbox/recon/odpt-2026-newplan/rtmod.py` は、この作業環境では空だった（レポート本文は主チェックアウトの `reports/recon/` から読んだ）。GTFS-RT パーサーは標準ライブラリで新規に書き、合成データの往復で検証した。

- **静的 GTFS の URL**: ページに無い事業者は、RT の URL から `files/odpt/<組織>/<名前>.zip` を推定して存在確認した（16 件で成功。5 件はページに URL があり、都営バスは既知の URL）。都営バスだけは現行アプリの `regions.json` の URL を使った。
- **夜間の短い取得（20 分・30 秒間隔・40 回）を手動で 1 回実行した**。指示の「品質測定」のためで、`--duration` で止まる。常駐ではない。

- 「事業者」の単位は CKAN のデータセット単位（同じ会社でも路線バスと空港バスは別）。
- 気づいた改善点（実装していない）: 位置データの蓄積を gzip 圧縮する、shapes による折れ線の補正、事業者の了承を得たうえでの停留所別の公開、現行アプリへの遅れ表示の組み込み。
