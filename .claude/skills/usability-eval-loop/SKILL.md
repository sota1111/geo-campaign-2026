# 使いやすさの評価ループ

2026-11-22 に、提出対象の6アプリ（クマ・路面下A・太陽光盗難・住む場所の先行き・大規模修繕・データセンター）で回したやり方を手順にしたもの。実績と教訓は末尾にある。

## いつ使うか
- 提出前に、画面を持つ成果物の目標達成度と使い勝手を上げたい時。
- 新しく作ったアプリが、初見の人に使えるかを確かめたい時。
- 総司令官から「評価ループ」「エージェントに評価させて直して」と言われた時。

次の役割の代わりにはならない。
- 憲兵の監査（要項への適合）
- デザイン審査班の審査

評価ループで重大が 0 になっても、提出可能・完成とは報告しない（CLAUDE.md）。

## 準備（参謀長がやる）
1. **対象と目的・目標を決める**
   - 目的は総司令官の原文をそのまま使う。
   - 目標は「初見の人が画面だけで確かめられる行動」で 3〜5 個にする。
   - 例: 「地図で建物を選ぶと、修繕費の目安の範囲が分かる」
   - README の説明は評価者に渡さない。
2. **作業用の worktree を、アプリごとに先に作る**
   ```bash
   git worktree add -b claude/engineer-evalloop-<key>-<YYYYMMDD> .claude/worktrees/evalloop-<key> origin/<既定ブランチ>
   ```
   ループの間、同じブランチにコミットを積む。`isolation: 'worktree'` は使わない（毎回新しい worktree になり、積み上がらない）。
3. **ポートをアプリごとに割り当てる**
   - アプリごとに 10 番ずつ空ける（例: 8700, 8710, …）。
   - 評価者 i は base+i、工兵は base+9 を使う。
   - 5180 は総司令官用なので使わない。
4. **ダッシュボードに別実装があるか確かめる**
   - 例: sat-a は単体と React 版の二重実装になっている。
   - あれば、工兵の指示に「両方直す」と書く。

## 回し方
`workflow.js`（このスキルのディレクトリにある）を Workflow ツールで実行する。args にアプリの一覧を渡す。

```js
Workflow({ scriptPath: '.claude/skills/usability-eval-loop/workflow.js', args: {
  maxRounds: 5,
  apps: [{ key, name, dir, web, page, portBase, purpose, goals: [...] }],
}})
```

- 総司令官が回数を指定した場合は、その回数で回す。`maxRounds` に入れ、`stopOnPlateau: false` にする。
- 指定がない場合は、打ち切り条件を使う。`stopOnPlateau: true` にすると、次の両方を満たした時に止まる。
  - 重大 0・未達 0
  - 平均点の伸びが 2 回続けて 0.3 未満
- Workflow は多数のエージェントを使う。総司令官の明示の指示がある時だけ回す（Workflow ツールの規定）。

### 評価者（1アプリにつき5体・sonnet）
- **渡すもの**: 目的、目標、アプリの開き方、評価の基準だけ。README やソースの説明は読ませない。
- **立場は5つに分ける**
  1. 実務担当者（初見）
  2. 審査員（短時間で価値を判断する）
  3. IT に不慣れな一般の利用者
  4. スマホ（390×844）だけで使う利用者
  5. データの根拠と誤解の起きやすさに厳しい専門家
- **操作のさせ方**
  - 自分でポートを使って配信させる（`python3 -m http.server`）。
  - headless の google-chrome を CDP で操作させ、1513×784 と 390×844 の両方でスクリーンショットを撮らせる。
  - 操作の書き方は、各アプリの `tests/ui_check.mjs` を参考にさせる。
- **評価の基準**
  - 目標ごとに 達成／一部／未達 を判定させる。
  - 縦スクロールの回数、画面遷移の回数、文字が多すぎる箇所を数えさせ、減点にする。
  - 指摘は重大・中・軽微に分けさせる。架空のデータを実データと誤解させる表示は重大。
  - 出力は構造化した JSON にする（スキーマは workflow.js にある）。

### 工兵（1アプリにつき1体・opus・agentType engineer）
- 5体の指摘を、次の優先順で直させる。
  1. 重大 → 中 → 軽微
  2. 複数の評価者が挙げた点を先に
  3. 目標の未達を最優先
- 縦スクロール・画面遷移・文字数を減らさせる。ただし、出典・ライセンス・架空の明示・責任表示は消させない（短くするのはよい）。
- アプリのテストとダッシュボードの build・vitest を通させ、1回ごとにコミットさせる（push はしない）。
- 直さなかった点は、理由と一緒に返させる。

## 終わった後（参謀長がやる）
1. 各ブランチに既定ブランチを取り込み、dashboard の vitest・build を確かめる。
2. push と PR を作る。
   - push は、そのブランチの worktree に `cd` した別のコマンドで行う。hook は、セッションの作業ディレクトリのブランチで push 先を判定するため。
   - `2>&1` や `2>/dev/null` を付けると hook に止められる。
3. PR 本文には、回ごとの「平均点・重大・中・未達・スクロール・画面遷移・コミット」の表と、直さなかった点を入れる。
4. 総司令官補佐に代理マージを任せる。
5. 必要なら、憲兵の監査とデザイン審査に回す。
6. 結果の要点（点数の推移、残った課題、データの制約）を総司令官に報告する。

## 教訓（2026-11-22 の実績から）
- **2〜3回目で頭打ちになる**
  - 6アプリとも、1回目→2回目で平均が +1.6〜+2.2 伸び、重大はほぼ 0 になった。
  - 3回目以降の伸びは ±0.3 程度で、中の件数も 10〜19 件から減りにくい。指摘を直すと別の指摘が出る。
  - 回数の指定がなければ、打ち切り条件で止める。
- **スクロールと画面遷移はトレードオフになる**
  - スクロールを 0 にすると、タブの切替が増える（例: 路面下A は5回目にスクロール 0、画面遷移 3〜9回）。
  - 両方を見て、増えた側を次の回の工兵に伝える。
- **評価者どうしが逆のことを言う**
  - 例: スマホのシートを高くしたい人と、低くしたい人がいた。
  - 工兵には、多数に合わせて判断ログに書かせる。
- **データの制約による指摘は、毎回出続ける**
  - 例: 大規模修繕の「類似マンションの公開の修繕実績がない」。毎回、重大や中として出る。
  - 2回出たら「データの制約」として扱い、総司令官の判断事項として報告する。工兵には直させない。根拠のない数値を作る原因になるため。
  - workflow.js は、工兵が `dataConstraint: true` と返した指摘を数えて次の回に渡す。ただし文言が回ごとに変わると同じ指摘と数えられないので、最後に参謀長が返り値の `dataConstraints` を読んで束ねる。
- **既存のテストが古い画面を前提にしている**
  - 工兵がテストを直すことを、指示に含める。
  - ただし、「架空の明示」「出典」の検査は外させない。
- **worktree の中では Write/Edit が書き込みガードに止められることがある**
  - guard_paths.py は本体リポジトリの絶対パスで判定している。
  - 工兵は Bash で書き込んで回避した。ガードの worktree 対応は未解決。
- **pkill がパターン一致で自分のシェルを落とす**（終了コード 144）
  - サーバーは起動時に PID を控えて `kill <PID>` で止める。
  - または、ポート番号で `fuser -k <port>/tcp` を使う。
  - 5180 のプレビューを巻き込んだ例がある。終わったら 5180 が動いているか確かめる。
- **費用の目安**
  - 5アプリ×5回（評価者125体＋工兵25体）で、サブエージェント約 1,090 万トークン、所要時間 約1.5時間。
  - 1アプリ×5回で、約 190 万トークン。
