## 結論
1280px 以上のデスクトップでは、カードだけで「締切・提出不可の理由・案ごとの済／残り・判断待ち・次にやること」が読める。前提（一覧は上に固定、押すと下の全幅欄に出る、自動スクロールなし、重ねるパネルなし）も守られている（下の「前提の確認」）。
ただし、**幅 1024px 以下（1024×768 のノートPC・iPad 縦横・640px）では詳細欄の高さがほぼ 0 になり、詳細を読めない**。これは重大。1280×765 でも詳細欄の中身は 185px しかなく、そこに見えるのはカードと同じ内容なので、実用ぎりぎり（中）。

### S1. 幅 1024px 以下で詳細欄がつぶれ、詳細が読めない

  | 768×1024（iPad 縦） | 31px | **24px** | なし |
  | 640×900 | 33px | **24px** | なし |
  | 820×1180 | 237px | 155px | なし |
  | 1280×720 | 194px | 140px | なし |
- スクリーンショット: `extra/d1024x768-top.png` の一番下（y≈681〜768。「衛星アワードの詳細」の見出しと1行だけ）、`t768x1024-top.png` の一番下（y≈985。見出しの上端だけで、中身は見えない）、`extra/m640x900-top.png` の一番下

- 1024×768 ではカードも崩れる: 「イチBiz」が「イ／チ／Biz」の3行に割れ、案の名前が「提…」「ビ…」「作…」と1文字で切れる（`extra/d1024x768-top.png` の 2列目の見出し、各カードの「案ごとの完了・残り」）
- 直し方の提案（どれか1つ、または組み合わせ）:
  1. 4列の大きいカード（ContestCard）は「本文の幅が 960px 以上、かつ画面の高さが 760px 以上」の時だけにする。それより小さい時は、スマホ用の高さ 6rem のカード（MobileCard）を 2列で並べる（768px なら 2行×100px＝約 200px で、残りが詳細欄になる）
  2. 詳細欄に最低の高さ（例: 画面の高さの 45%）を持たせ、足りない時はカードを短い形に切り替える
  3. 1024px 以下ではサイドバーを最初から閉じる（本文の幅が 256px 広がる）
  - どれでも前提（一覧が上・その場で詳細・自動スクロールなし・重ねない）は保てる
- 確かめ方: 1024×768・768×1024・640×900 で、詳細欄の中身の高さが 250px 以上あること

## 中（迷い・手戻りを生む）

### M1. 1280×765／800 の詳細欄は 185〜220px で、見えるのはカードの繰り返し
- 根拠: 詳細欄の中身の高さは 1280×765 で 185px、1280×800 で 220px、1440×900 で 320px。中身の全体は 2,859px（衛星）で、1280×765 だと約15画面分を小窓でスクロールすることになる。最初に見える 185px の中身は「▲ 提出不可（判断待ち）: …」「締切 11/30 正午 あと8日」「提出可能か …」で、**どれも真上のカードに書いてある内容**。新しい情報は「済んだこと」の1行だけ（`d1280x765-top.png` の y≈580〜740、`d1280x800-top.png` の y≈575〜790）
- 「第3回の比較へ」を押すと、レーダー図が 220px に入らず、上半分しか見えない（`d1280x800-jump-eval3.png` の y≈570〜790）
- なぜ問題か: スクロール観点・視覚階層観点。工兵の申告（約270px）は外枠の高さで、中身は 220px。小窓での長いスクロールは、どこまで読んだか分からなくなりやすい
- 直し方の提案:
  - カードを短くする（いまは 434px）。たとえば「▲ 提出可否: 提出不可。…」の3行は、カード右上の状況バッジと上の帯「どの案も提出不可」と重なるので、カードからは外して詳細欄に任せる。案の行はイチBizの7行が高さを決めているので、「提出予定」の案だけ並べて残りは「ほか比較中 4案」にまとめる。合わせて 280px 前後にすれば、1280×765 で詳細欄の中身が約 330px になる
  - 詳細欄の先頭の「▲ 提出不可（…）」の行と「提出までの状況」の締切・提出可能かの行は、カードと同じなので省くか、たたんでおく。詳細欄は「済んだこと」と「判断待ちの選択肢」から始める
- 要確認（判断が割れる点）: カードを短くすると「カードだけで分かる」量が減る。案A＝カードを短くして詳細欄を広げる（上の提案）／案B＝カードはそのままにし、詳細欄から重複を消すだけにする（185px でも新しい情報から始まる）。総司令官が普段 1280×800 前後で見るなら案A を勧める

### M2. 「？」の数が、案ごとの合計と「総司令官の判断待ち ◯件」で合わない
- 根拠: `d1280x800-top.png` の各カード
  - 衛星: 案の行は「藪払い・スギ ？1」「新案α ？1」で計2、その下の黄色い枠は「総司令官の判断待ち 1件」
  - イチBiz: 「アイデア IN1 ？2」「不動産 RN1 ？2」で計4、枠は「2件」
  - ODPT: 「N2 定時性 ？2」「子連れ ？1」で計3、枠は「2件」
- 実装では、案の行の「？」は「判断待ち・要確認」の合計（ContestCards.tsx の sr-only 文「うち判断待ち・要確認」）で、黄色い枠は総司令官の判断だけを数えている。同じ記号で別のものを数えている
- なぜ問題か: 一貫性観点・文言観点。総司令官が一番知りたい「自分が決めることはいくつか」で、数が2通りに見える。デスクトップには記号の説明もない（M3）ので、見た目では区別できない
- 直し方の提案: 案の行の記号を「要確認」用の別の記号・言葉（例:「要確認 2」）に変える。または、案の行でも総司令官の判断の数だけを「？」で示し、合計が枠の件数と一致するようにする

### M3. デスクトップ（1024px 以上）では「✓ 済 □ 残り ？ 判断待ち」の凡例が消える
- 根拠: 凡例は Portal.tsx の header にあり、`lg:hidden`。768px・640px・390px では出る（`t768x1024-top.png` の y≈62、`m390x844-top.png` の y≈68）が、1280px では出ない（`d1280x800-top.png` の y≈50〜70 は「どの案も提出不可」「マージ保留」の帯だけ）。「カードを押すと下の欄に詳細が出ます」という案内もデスクトップでは出ない
- なぜ問題か: 文言観点。「✓2 □3」はなんとか読めても、黄色の「？1」が何か分からない。M2 の食い違いと重なって、読み違えやすい
- 直し方の提案: デスクトップでも、上の帯の右端に凡例を1行で出す（帯には左側の2項目しかなく、右側が空いている）。「カードを押すと下に詳細」もそこに入れる

### M4. 審査待ちのアプリにも、普通のアプリと同じ「開く →」「このアプリを開く」の主ボタンがあり、開くと空の枠になる
- 根拠:
  - 詳細欄のアプリカード（ODPT の観光・冠水）: 「審査待ち（PR #36）…このビルドには含まれていません」の直後に「元の静的版をそのまま表示します（実行サンプルなし）」とあり、紺の「開く →」が普通のアプリと同じ見た目で出る（`d1280x800-odpt-detail-pending.png` の y≈630〜770）。2つの文が食い違う
  - コンペ概要ページ: 藪払い・スギ植え替えのカードにも、紺の「このアプリを開く →」（`d1280x765-contest_satellite-2026-pending.png` の y≈465〜495）
  - 押した先: 黄色い案内と目的の2行のあと、高さ約 500px の白い枠が空のまま（`d1280x765-apps_sat-yabu.png` の y≈240〜740、`m390x844-apps_odpt-kodure.png` の y≈400〜815）。案内を読まないと「読み込みに失敗した」ように見える
- なぜ問題か: 状態表示観点・視覚階層観点。主ボタンは「押せば使える」という約束なので、行き止まりに主ボタンを付けると手戻りになる
- 直し方の提案:
  - 審査待ちの間は、ボタンを外枠だけの控えめな見た目にし、文言を「概要だけ見る（未収録）」にする。または外して「PR #36 を見る」の文字リンクにする
  - 「元の静的版をそのまま表示します」は、審査待ちの時は出さない
  - アプリのページの空の枠は、外すか、枠の中央に「このビルドには未収録です（PR #36 のマージ後に表示）／今の案『盛土巡視台帳』を開く」という空の状態の表示を置く

### M5. カードの案の行から、どの案のアプリが審査待ち（未収録）か分からない
- 根拠: 衛星カードの「藪払い・スギ」、ODPT カードの「観光・冠水」「子連れ」、イチBiz カードの「太陽光 盗難対策」は、どれもアプリがこのビルドにない案だが、カードでは「比較中 ✓◯ □◯」と、ほかの案と同じに見える（`d1280x800-top.png` の各カードの「案ごとの完了・残り」）。サイドバーでは同じアプリに「審査待ち（PR #36）・未収録」の枠が付いている（同じ画像の左端 y≈600、740）
- なぜ問題か: 一貫性観点。カードを見て「アプリを確かめよう」と詳細やアプリへ進むと、M4 の行き止まりに当たる。PR のマージは総司令官（または補佐）の判断なので、「次に何をするか」にも関わる
- 直し方の提案: 案の行の名前の後ろに小さく「未収録」（サイドバーと同じ黄色い枠・同じ言葉）を付ける。幅が足りなければ、名前の前に「⌛」と sr-only の「審査待ち」

### M6. スマホのカードに残り日数・判断待ちの中身がない
- 根拠: `m390x844-top.png` の4枚のカード。「締切 11/30 正午」は出るが「あと8日」がない（デスクトップのカードにはある）。「？判断待ち 1件」の中身（何を決めるか）は、詳細欄をスクロールしないと出ない。詳細欄の中身は 192px（`m390x844-click3-scrolled.png`）
- なぜ問題か: 第一画面観点。スマホで「自分が決めることは何か」を知るのに、小窓のスクロールが必要になる
- 直し方の提案: 3段目の「？判断待ち 1件」を「？判断: B とαのどちらを出すか…」のように、最初の判断を1行で切って出す（件数は末尾に「ほか1件」）。締切の後ろに「（あと8日）」を足す。カードの高さ 6rem は変えずに入る

## 軽微（見た目・一貫性）

- L1. **詳細欄の見出し右の主ボタンが「第3回の比較へ」**（太枠・アイコン付きで、この画面で一番目立つボタン）。総司令官の目的（済んだこと・判断）に対しては二次的。外枠だけの控えめな見た目にそろえるか、詳細欄の中の評価の節に移す（`d1280x800-top.png` の y≈544）
- L2. **ボタンの言葉が場所によって違う**: 詳細欄のアプリカードは「開く →」、コンペ概要ページは「このアプリを開く →」。審査待ちの言葉も、サイドバーは「審査待ち（PR #36）・未収録」、カードとページは「審査待ち（PR #36）:」。どちらかにそろえる（`d1280x800-odpt-detail-pending.png`、`d1280x765-contest_satellite-2026-pending.png`）
- L3. **カードの中の「▲」の重複**: 状況バッジ「▲ 判断待ち」、「▲ 提出可否: 提出不可。」、上の帯「▲ どの案も提出不可」と、全カードに同じ記号と同じ結論が3回出る。差が出るのはバッジの言葉だけなので、カードの「▲ 提出可否」行は記号を外すか、M1 のとおり外す
- L4. **キーボードで本文に飛ぶ手段がない**: ページを開いて Tab を押すと、サイドバーの見出し・検索欄・各アプリのリンクを順に通る（8回押してもまだサイドバーの5件目）。最初に「本文（進捗カード）へ移る」のリンクを置く。なお、カードのフォーカス表示（紺の太枠、`d1280x800-focus-card2.png` の2枚目）と上下の矢印キーでの移動、Enter での切り替えは問題なく動いた
- L5. **詳細欄の中の枠が二重**: 詳細欄の外枠（灰色の太線）の中に、「提出までの状況」の角丸の枠がもう1つあり、狭い欄の幅と高さをさらに使う（`d1280x800-top.png` の y≈605〜800）。内側の枠は線を外して、見出しの下線だけにする

## 良い点（直さずに残すこと）
1. **カードを押しても一覧が1pxも動かない**。高さ固定とカードの位置の固定が、デスクトップ・スマホのどちらでも守られている。P-3 の目標をそのまま満たす作りなので、S1・M1 の修正でもこの性質は残すこと
2. **カードの中の順番**（締切と残り日数 → 提出可否 → 案ごとの済／残り → 総司令官の判断待ち（黄色の左線） → 次にやること）が、総司令官の問い「何が終わり、次に何をし、自分は何を決めるか」の順に合っている。判断待ちだけ色と左線で目立たせている点も良い
3. **色に頼らない区別**: 状況は「▲」と言葉、案の見込みは「提出予定＝実線の太字／比較中＝破線」と言葉で分けていて、白黒でも読める。スマホのカードも 6rem の固定で、選んでも大きさが変わらない
